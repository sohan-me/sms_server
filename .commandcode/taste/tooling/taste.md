# Tooling

- Deployment stack: Python Flask app served by gunicorn under pm2 on a VPS (project at /var/www/Orbit/sms_server with .venv); user manages processes via pm2 and tailing logs. Confirmed to run MULTIPLE gunicorn workers, not one. Confidence: 0.9
- Multi-worker means every fix must hold per-process: shared env must reach all workers, and boot-time DB setup must be race-safe (a single-process assumption produces a fix that looks correct and still fails on his VPS). Confidence: 0.85
- Redis runs locally on the SAME VPS as the app — `redis://127.0.0.1:6379/0` is correct; no host IP, LAN binding, or multi-machine fan-out setup needed for this project. Confidence: 0.9
- Invoke venv tools through the interpreter module form (`venv/bin/python -m pip install ...`, `venv/bin/python -m gunicorn`), never the `venv/bin/<tool>` console script. The project's venv was copied from another machine, so its bin/ scripts carry hardcoded absolute-path shebangs pointing at a path that no longer exists — console scripts silently install/run in the wrong place. Confidence: 0.9
- The project's deployment files live in the repo as templates he can copy to the VPS: `gunicorn.conf.py` (must use `worker_class = "gthread"` — the default `sync` worker cannot serve long-lived WebSockets and stalls other clients sharing the worker) and `ecosystem.config.js` (pm2 process definition, where the `env` block is the only thing that actually reaches workers). Never start `app.py` directly under pm2 — its `debug=True` dev-server reloader spawns a duplicate process that opens a second Redis subscriber. Confidence: 0.85
- Changing the start command on the VPS requires `pm2 delete <existing-name>` then `pm2 start ecosystem.config.js` — `pm2 restart` replays the previously configured command, so it silently keeps running the old one. Finish with `pm2 save` to survive reboot. Check `pm2 list` first: a leftover process on the same port means two servers fighting over it. Confidence: 0.85

# Workflow

- Plan-driven execution: when a plan is attached, implement exactly as specified. Do NOT edit the plan file. To-dos already exist — never recreate them; mark each in_progress as you work, starting with the first, and don't stop until all are complete. Confidence: 0.95
- Push to git at the end of each work cycle — "push into git" is the user's standard closing request after features/fixes. Confidence: 0.9
- Verify work with runnable tests before calling it done; user asks for proof (e.g., send a real SMS and receive it over WS, test with multiple users/tokens). Confidence: 0.85
- Proof should be empirical and adversarial, not just "tests pass": reproduce the reported failure first, then the fix, and include a negative control (revert the config → observe the original broken behavior) to confirm the diagnosis rather than assert it. He responded well to "0,1,2,3 of 6 received without Redis; 6/6 with it". Confidence: 0.85
- A fix for a multi-worker production bug is not verified until it runs under real gunicorn with real workers. Run the actual server with multiple workers, probe the health endpoint per PID, and fix whatever breaks — the first two attempts at the gunicorn boot both failed in ways the unit/e2e tests could not catch. Confidence: 0.8
- When a shell command kills its own process group (e.g. `pkill -f` matching the invoking shell), switch to targeted PIDs filtered against `$` rather than retrying the same command. Confidence: 0.75
- When debugging, user reports symptoms plus a suspected cause and asks "why it's happening" — answer with a root-cause diagnosis that validates or refutes their hypothesis (backed by evidence like tests/logs), not just a fix. Confidence: 0.7
- When the user proposes a rewrite / new framework ("should we modify this or create another server with FastAPI?"), resist the migration by first mapping each step of their proposed flow to the code that already implements it (file:line) and naming the operational risk of a rewrite (e.g. reproducing the same bug in a new codebase). Fix configuration/deployment before changing architecture. Confidence: 0.8
- When a change touches deployment config, the answer isn't "done" until the user has an ordered runbook for the VPS: numbered, copy-pasteable commands, which values to edit, and a verification step that can actually fail. He asks "what i need to do on VPS after pulling the repo?" — expect this and hand it over unprompted.
- That runbook must include a loop-style health check with a stated pass condition (e.g. "curl the health endpoint ~8 times; you need different PIDs each reporting `redis_subscriber_alive: true`"), plus the gotchas he'd otherwise hit: stale pm2 process still bound to the port, env vars that must carry over into the ecosystem file, and reverse-proxy WebSocket headers. Confidence: 0.8
- At a genuine fork, use ask_user_question to lay out the options with a clearly marked recommended default rather than an open-ended question. He took the recommended path without pushback, so lead with the recommendation instead of presenting choices neutrally. Confidence: 0.6
